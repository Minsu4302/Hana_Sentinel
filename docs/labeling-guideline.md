# 라벨링 지침 v1 — S 데이터셋

> 버전: v1. 정본: (A) `docs/design-decision.md` §6.2. 충돌하면 (A)가 우선한다.
> 조항마다 근거를 적는다. 사례 카탈로그는 hard negative의 근거를 이 지침의 조항 ID로 적는다.
> 한계: positive는 관측 신호이고 악용 가능성이 아니다.

## 제0장 원칙

- **G-1 도출:** 이 지침은 (A) §1.1 카테고리 정의와 ①~④ 경계 문장에서만 도출한다. anchor는 §6.1 지침을 따른다.
- **G-2 독립:** 규칙·생산자를 보고 설계하지 않는다. 이 지침은 규칙의 패턴·조건을 인용하지 않는다. 규칙을 아는 작성자의 편향은 1인 단계 한계다((A) §6.2).
- **G-3 버전과 동결:** 지침은 카탈로그 작성 전에 동결한다. 변경은 새 지침 버전과 새 데이터셋 버전으로만 한다.

## 제1조 관측 가능성

- **O-1:** 라벨은 마스킹 후 트랜잭션에서 관측 가능한 근거로만 판정한다. 근거: §1.1 기준(단일 트랜잭션 안에서 신호 관측 가능).
- **O-2:** 마스킹된 값의 내용은 근거가 될 수 없다. relation_preserving 라벨의 같음·다름은 값이 아니라 관측 가능한 관계이므로 근거가 된다. 근거: §1.1 기준, §1.1 ①의 경계, (A) §2.3.
- **O-3:** 판정할 수 없는 사례는 S에 넣지 않는다. 제외 목록에서 관리한다. 근거: §1.1 기준.
- **O-4:** 관측이 같은 두 트랜잭션은 라벨이 같다. 배경만 다른 사례는 관측상 같은 positive로 라벨하고, 그 배경의 사례를 따로 구성하지 않는다. 근거: (A) §6.2.

## ① access_control

- **AC-P1 positive:** relation_preserving에서 요청 주체 라벨과 응답 객체 소유자 라벨이 다르다. 근거: §1.1 ①의 경계.
- **AC-N1 hard negative:** 요청 주체 라벨과 응답 객체 소유자 라벨이 같다. 근거: §1.1 ①의 경계(주체가 관측상 다르지 않음).
- **AC-S1 같은 관측:** 다른 사람의 객체가 정당하게 공개되는 경우. 관측상 AC-P1과 같으므로 AC-P1로 라벨하고, 그 배경의 사례를 따로 구성하지 않는다. 근거: O-4.
- **AC-X2 제외:** strict_redaction 사례. 라벨이 null이라 비교할 수 없다. 근거: O-2, O-3, (A) §2.3.

## ② info_exposure

- **IE-P1 positive:** 응답에 서버 측 스택 트레이스가 있다. 근거: §1.1 ②의 경계.
- **IE-P2 positive:** 응답에 DB/ORM 오류 메시지가 있다. 입력과의 연관은 묻지 않는다. 근거: §1.1 ②의 경계.
- **IE-P3 positive:** 응답에 서버 파일시스템 경로가 있다. 근거: §1.1 ②의 경계.
- **IE-N1 hard negative:** 서버 내부 정보가 없는 일반 오류 응답. 근거: §1.1 ②의 경계(내부 정보가 관측되지 않음).
- **IE-S1 같은 관측:** 의도된 예시 문자열인 경우. 관측상 IE-P1~P3과 같으므로 그 조항으로 라벨하고, 그 배경의 사례를 따로 구성하지 않는다. 근거: O-4.

## ③ security_misconfig

positive는 아래 닫힌 목록뿐이다(§1.1 ③의 경계). 목록 변경은 지침 버전 변경이다.

- **SM-P1 positive:** 응답이 허용 출처 와일드카드와 자격증명 허용을 함께 선언한다. 근거: §1.1 ③의 경계.
- **SM-P2 positive:** 응답이 요청의 Origin 값을 허용 출처로 되돌리면서 자격증명 허용을 선언한다. 근거: §1.1 ③의 경계.
  - 구성 조건: Origin은 비어 있지 않고 요청 host와 다른 호스트다. 요청 host는 마스킹되어 Envelope에서 비교할 수 없으므로 판정 근거가 아니라 카탈로그의 구성 조건이다.
- **SM-P3 positive:** 응답 본문이 서버 생성 색인 페이지 형식이다. 형식은 제목 `Index of <경로>`, 상위 디렉터리 링크, 파일 항목 목록을 모두 갖춘 것이다. 근거: §1.1 ③의 경계.
- **SM-P4 positive:** https 응답이 HSTS를 `max-age=0`으로 끈다. 근거: §1.1 ③의 경계.
- **SM-P5 positive:** 응답의 허용 메서드 선언에 TRACE가 있다. 근거: §1.1 ③의 경계.
- **SM-N1 hard negative:** 허용 출처 와일드카드이고 자격증명 허용이 없다. 근거: §1.1 ③의 경계(SM-P1의 조합이 아님).
- **SM-N2 hard negative:** 자격증명을 허용하지만 허용 출처가 요청 Origin과 다른 고정 값이다. 근거: §1.1 ③의 경계(SM-P2의 되돌림이 아님).
- **SM-N3 hard negative:** HSTS가 양수 max-age로 켜져 있다. 근거: §1.1 ③의 경계.
- **SM-N4 hard negative:** 허용 메서드 선언에 TRACE가 없다. 근거: §1.1 ③의 경계.
- **SM-N5 hard negative:** 링크 목록이 있지만 SM-P3의 형식(제목 `Index of <경로>`와 상위 디렉터리 링크)을 갖추지 않은 페이지. 근거: §1.1 ③의 경계.
- **SM-S1 같은 관측:** CORS 허용 목록 일치로 Origin을 되돌린 경우. 관측상 SM-P2와 같으므로 SM-P2로 라벨하고, 그 배경의 사례를 따로 구성하지 않는다. 근거: O-4, (A) §6.2.
- **SM-X2 제외:** 값이 마스킹되는 헤더의 오설정(Set-Cookie 플래그 등). 근거: O-2, O-3.

## ④ reflected_injection_indicator

정의:

- **RI-D1 주입 의미 문자:** 응답의 HTML·JS 구문을 바꿀 수 있는 문자 `<` `>` `"` `'` `` ` ``. 근거: §1.1 ④의 경계. 규칙과 달라 보이려 넓히지 않는다(역방향 편향).
- **RI-D2 SQL 의미 문자:** `'` `"` `;` `--`. 근거: §1.1 ④의 경계(응답에 SQL 에러 문자열).
- **RI-D3 요청 값:** 평문으로 관측되는 쿼리·폼 파라미터 값, 경로, 헤더 값, 본문 값. 근거: §1.1 ④의 경계, O-2.
- **RI-D4 원형:** 응답 값을 그 본문 형식의 구문으로 해석한 뒤의 값이 요청 값과 같다. JSON 문자열의 구문 이스케이프는 이스케이프로 보지 않는다. 근거: §1.1 ④의 경계(값이 같은 응답에 반사됨).

조항:

- **RI-P1 positive:** 주입 의미 문자를 포함한 요청 값 전체가 응답에 원형으로 반사된다. content-type은 묻지 않는다. 근거: §1.1 ④의 경계(값이 같은 응답에 반사됨).
- **RI-P2 positive:** 요청 값에 SQL 의미 문자가 있고 응답에 SQL 에러 문자열이 있다. 입력과의 연관이 이 두 관측으로 드러난다. 라벨은 2개다(② IE-P2 / ④). 근거: §1.1 ④의 경계(응답에 SQL 에러 문자열), §1.1 ②의 경계.
- **RI-N1 hard negative:** 주입 의미 문자가 이스케이프된 반사. 근거: §1.1 ④의 경계(값이 같게 반사되지 않음).
- **RI-N2 hard negative:** 주입 의미 문자가 제거된 부분 반사. 근거: §1.1 ④의 경계.
- **RI-N3 hard negative:** 주입 의미 문자가 없는 값의 에코. 근거: §1.1 ④의 경계.
- **RI-C1 대조 사례:** 입력과 무관한 DB 오류(요청 값에 SQL 의미 문자가 없음). ④ 라벨이 없고 ② 라벨(IE-P2)만 있다. positive 트랜잭션이므로 hard negative로 세지 않는다. 근거: §1.1 ④의 경계, (A) §6.2 규모 게이트.
- **RI-X1 제외:** 값의 일부가 주입 의미 문자와 함께 반사되어 RI-P1도 RI-N2도 아닌 경우. 정의 경계 사례로 v1에서 정하지 않는다. 근거: O-3.

## 라벨 수와 categories

- **L-1:** labeled_positive는 결함마다 1개다. 한 트랜잭션에 결함이 둘이면 라벨이 2개다(예: RI-P2). 근거: (A) §6.2 라벨 모델.
- **L-2:** categories 집합은 단일 결함의 category가 모호할 때만 쓴다. 근거: (A) §6.2 라벨 모델.
- **L-3:** hard negative는 verified_clean 트랜잭션에만 있고, 그 트랜잭션의 유일한 라벨이다. 근거: (A) §6.2 라벨 모델.

## anchor

(A) §6.1을 따른다. 더 세밀한 노드가 있으면 거친 노드(body_text·req_line.path)를 쓰지 않는다. verified_clean은 anchor가 없다((A) §6.2). anchor는 라벨마다 적는다.

| category | anchor |
|---|---|
| ① | 요청 주체 라벨이 있는 헤더 + 소유자 라벨이 있는 응답 노드 |
| ② | 내부 정보가 있는 응답 노드 전부 |
| ③ | 판정에 쓴 헤더 전부(SM-P2는 요청 Origin 포함). SM-P3은 색인이 있는 응답 노드 |
| ④ | 요청 값 노드 + 반사된 응답 노드 전부. RI-P2는 요청 값 노드 + SQL 에러 문자열이 있는 응답 노드 |

경로에서 온 요청 값의 anchor는 `req_line.path`를 쓴다(더 세밀한 노드가 없다).
