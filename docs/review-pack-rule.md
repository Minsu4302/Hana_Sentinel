# 리뷰 팩 규율 — Sentinel Harness

> 단일 출처. 부트스트랩·CLAUDE.md는 이 파일을 가리키기만 하고 내용을 다시 적지 않는다.
> 목적: 리뷰어가 전문 없이 '요지 + 포인터'만으로 정본 정합성을 판정하게 한다.

## 1. 분류
- [CORE]: 안전 경계(입력·출력·민감정보·실행)를 바꾸는 작업, 정본 (A) 개정,
  안전 불변식에 걸린 manifest 승격.
- [ROUTINE]: docs 정리, 추적용 등재, 안전 불변식에 닿지 않는 작업.
- 분류는 발주문이 정한다. 작업 중 CORE 성격이 드러나면 구현자가 상향하고 사유를 적는다.
  하향은 금지한다.

## 2. 형식 (순서 고정, 해당 없으면 "없음"이라고 적는다)
0. 머리: [분류] 항목 ID / Issue # / PR # / 브랜치 /
   make verify 종료코드 + selfcheck 활성 표지 확인 여부
1. 요지: 무엇을 했나, 3~5줄.
2. manifest 변화: 키 | 이전 → 이후 | 증명 테스트 노드.
   마지막에 "enforced 집합 diff" 한 줄.
3. 적대 테스트: 케이스 → 기대 동작(거부) → 테스트 노드.
4. 변이 확인: 무력화한 검사 → 실패한 테스트. 변이본이 실제로 로드됐는지 확인했는지 여부.
5. 정본 대비: (A) 변경 여부(절·사유) /
   정본이 정하지 않은 지점에서 내린 재량 결정(선택값·이유·대안).
6. 멈춤 조건: 발동 여부. 발동했다면 무엇이 어떻게.
7. 깨진 가정 / 미해결: progress-log에 반영한 위치.
8. 리뷰어가 볼 곳: [CORE]는 최대 3곳(파일:심볼 또는 테스트 노드). [ROUTINE]은 생략 가능.

## 3. 규칙
- 전문(코드·diff·로그 원문)을 붙이지 않는다. 포인터만 적는다.
- '구현했다'가 아니라 '어떤 테스트가 무엇을 거부했다'로 쓴다.
- 테스트 개수 같은 수치를 성과로 내세우지 않는다.
- 비밀값·토큰·원문 트래픽은 더미라도 팩에 넣지 않는다. 값 대신 패턴 이름을 적는다.
- 리뷰어 확인 범위: [ROUTINE]은 2·3번, [CORE]는 전부(특히 5번).
