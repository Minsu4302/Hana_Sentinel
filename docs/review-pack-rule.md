# 리뷰 팩 규율 — Sentinel Harness

> 단일 출처. 부트스트랩·CLAUDE.md·구현자 메모리는 이 파일을 가리키기만 하고 내용을 다시 적지 않는다.
> 목적: 리뷰어가 전문 없이 '요지 + 포인터'만으로 정본 정합성을 판정하게 한다.

## 1. 분류
- [CORE]: 안전 경계(입력·출력·민감정보·실행)를 바꾸는 작업, 정본 (A) 개정,
  안전 불변식에 걸린 manifest 승격.
  예: 토큰 검증, sanitization, egress, 출력 게이트, manifest 자기검증.
- [ROUTINE]: docs 정리, 추적용 등재, 안전 불변식에 닿지 않는 작업.
- 분류는 발주문이 정한다. 작업 중 CORE 성격이 드러나면 구현자가 상향하고 사유를 적는다.
  하향은 금지한다.

## 2. 형식 (순서 고정, 해당 없으면 "없음"이라고 적는다)
제목 줄: `## 리뷰 팩 — [분류] <항목 ID>`

0. 머리: Issue # / PR # / 브랜치 / make verify 종료코드(첫 실행인지 재실행인지) /
   selfcheck 활성 표지 확인 여부 / guardrails check 결과
1. 요지
   - 첫 줄: 이 작업으로 무엇을 보장하게 됐나(1문장).
   - 이어서: 무엇을 했나(3~5줄).
2. 변경 파일: 경로 | 핵심 변경 한 줄. 의도하지 않은 변경(개행·서식 등)도 적는다.
3. manifest 변화: 키 | 이전 → 이후 | 증명 테스트 노드.
   마지막에 "enforced 집합 diff" 한 줄.
4. 적대 테스트: 케이스 → 기대 동작(거부) → 테스트 노드.
5. 변이 확인: 무력화한 검사 → 실패한 테스트. 변이본이 실제로 로드됐는지 확인했는지 여부.
6. 정본 대비
   a. 참조한 (A) 절 번호 — 변경이 없어도 적는다.
   b. (A) 변경 여부(절·사유).
   c. 정본이 정하지 않은 지점에서 내린 재량 결정: 선택값 | 이유 | 대안.
   d. 발주문에서 벗어난 판단(정본 범위 안이라도): 무엇을 | 왜.
   e. (A) 개정 제안: 있으면 여기에 따로 적고, 멈춤 조건이 발동한 것으로 간주한다
      (구현을 진행하지 않고 보고한다).
7. 멈춤 조건: 발동 여부. 발동했다면 무엇이 어떻게.
8. 깨진 가정 / 미해결: progress-log 반영 위치 + 이월처(주차·주제).
9. 리뷰어가 볼 곳: [CORE]는 최대 3곳(파일:심볼 또는 테스트 노드). [ROUTINE]은 생략 가능.

## 3. 규칙
- 전문(코드·diff·로그 원문)을 붙이지 않는다. 포인터만 적는다.
- '구현했다'가 아니라 '어떤 테스트가 무엇을 거부했다'로 쓴다.
- 테스트 개수 같은 수치를 성과로 내세우지 않는다.
- 비밀값·토큰·원문 트래픽은 더미라도 팩에 넣지 않는다. 값 대신 패턴 이름을 적는다.
- PR 본문은 PR 템플릿을 따르고, 리뷰 팩은 최종 보고로 따로 낸다.
- 결산처럼 특별히 요청받은 첨부물은 팩 뒤에 덧붙인다.
- 리뷰어 확인 범위: [ROUTINE]은 1·3·4번, [CORE]는 전부(특히 2·6번).
